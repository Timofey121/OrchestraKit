# Проверка рабочего процесса на задачах

Набор помогает сравнить варианты Orchestra на одинаковых заданиях. В него входят
загрузка CSV, фильтрация путей архива, TTL-кэш, JSON-хранилище задач, рефакторинг
агрегации продаж, разбор цепочки вызовов и два расследования неподтверждённых
ошибок в уже правильном коде. Все проекты учебные, без личных данных
и внешних зависимостей. Они проверяют работу с Python, а не все языки и проекты.

## Подготовка и запуск

Нужны Python 3.11+ и авторизованный Codex CLI. Нативный запуск исполнителей
требует macOS, Linux или WSL. Подготовка, проверка и чтение отчёта работают локально
и не вызывают модели.

```bash
./bin/orchestra eval list
./bin/orchestra eval prepare \
  --output .orchestra/checks/eval-baseline --variant baseline --repeat 2

# Эта команда вызывает модели и расходует лимит Codex.
./bin/orchestra eval run .orchestra/checks/eval-baseline --max-launches 32 --timeout 180

./bin/orchestra eval report .orchestra/checks/eval-baseline
```

Восемь заданий с двумя повторениями дают 16 отдельных рабочих каталогов.
Для первой успешной попытки с ревью всех заданий нужны 32 запуска CLI.
Каждое успешное решение проходит тесты и отдельное ревью. При провале
исполнителя ревью не запускается, а расход неудачной попытки остаётся в отчёте.
Профили берутся из конфигурации каждого созданного тестового проекта. Они
используют обычные шаблоны Orchestra; настройки твоего рабочего проекта
автоматически не копируются. Главная модель текущего чата не меняется.

По умолчанию автоматических повторов нет: это замер первой попытки с ревью.
Для исследования ремонтов при подготовке укажите `--repair-cycles 1` или `2`.
Используется общий цикл `workflow`: исправления возможны после провала тестов
и после замечаний ревьюера. Они расходуют один общий лимит исправлений.
Перед каждой задачей запуск резервирует место для всех разрешённых попыток
исполнителя и проверяющего. Поэтому остатка лимита может не хватить на следующую
задачу, даже если предыдущие использовали меньше вызовов. `--max-launches` учитывает
уже записанные попытки этой серии при повторном запуске команды. Это ограничение
числа запусков Codex CLI. Один запуск может включать несколько внутренних
обращений к модели. Набор не задаёт жёсткий предел этих обращений, токенов
или денег. `--max-calls` оставлен как синоним той же настройки.

Для небольшой проверки выберите задание через `--case`, например
`--case ttl-cache-bounds`, и задайте `--repeat 1`. Результаты хранятся в указанном
новом каталоге; команда подготовки не перезаписывает существующий.

## Что считается результатом

Модель получает исходники и требования. Проверяющий получает исходную задачу
и итоговые файлы. Эталонное решение и приёмочные тесты не передаются в brief.
Тесты запускаются хостом из отдельного каталога. Изменение тестов, фиксированных
исходников или файлов вне разрешённой области не превращается в успешный ответ.
Это защита от случайного изменения проверки, а не изоляция от злонамеренной модели
с доступом ко всем файлам компьютера.

В отчёт входят все записанные попытки исполнителя и проверяющего. Входные токены
уже содержат кэш; токены рассуждений входят в выходные. Пропущенные счётчики
остаются неизвестными. Расход разработки набора и скрытая работа хоста сюда не
входят. Названия моделей отражают запрошенные настройки запуска.

Для успеха нужны пройденные тесты, соблюдение области изменений и независимый
`VERDICT: PASS`. Отчёт заново запускает приёмочные тесты и проверяет, что исходники
после ревью не изменились. Изменённый результат требует новой серии.

Прерванный запрос не повторяется автоматически. Если остался `started.json`
без `result.json` или файл `running.lock`, сначала разберитесь с процессом
и сохранёнными журналами. Удаление маркера само по себе не доказывает, что запрос
не выполнился и не потратил токены.

## Контроль лишних исправлений

Задания `half-open-interval-not-reproduced` и `ttl-expiry-not-reproduced`
проверяют расследование ложного сообщения о баге. Производственный модуль
в каждом задании уже правилен. Исполнитель получает описанный контракт,
входные данные для целевых проверок и формат краткого `report.json`.

Полный исходный результат не проходит оценщик, потому что отчёта ещё нет.
Это не означает, что исходный производственный код сломан. Правильное решение
сохраняет его байты и записывает проверяемые наблюдения. Оценщик отдельно
запускает поведение, проверяет факты отчёта и отклоняет ненужную правку,
даже если она только меняет оформление кода. Для этих заданий сохранение байтов
является явным критерием; для обычных исправлений побайтовое совпадение
с исходником не требуется.

Шесть прежних заданий сохранены: отказ исправлять настоящую ошибку или
реализовать запрошенную функцию не должен улучшать результат серии. Контрольные
задания не доказывают отсутствие лишних правок на любых проектах и сами по себе
не показывают экономию токенов.

## Сравнение с изменённым процессом

Сохраните исходную серию. После изменения поведения подготовьте новую с другим
именем варианта, теми же заданиями, числом повторений и настройками моделей:

```bash
./bin/orchestra eval prepare \
  --output .orchestra/checks/eval-candidate --variant candidate --repeat 2
./bin/orchestra eval run .orchestra/checks/eval-candidate --max-launches 32 --timeout 180
./bin/orchestra eval compare \
  .orchestra/checks/eval-baseline .orchestra/checks/eval-candidate
```

Команда использует существующий `compare-workflows`. Сравнение требует полных
серий и счётчиков, одинаковых исходных задач, окружения и начальных моделей.
Рекомендация возможна только при меньшем общем числе токенов, успехе всех
заданий кандидата и отсутствии ухудшения по заданиям. Одна базовая серия
экономию не подтверждает. Даже успешное сравнение относится к этому набору;
для решений о маршрутизации нужны дополнительные проекты и повторения.

В отчёте `accepted_trials` и `unresolved_trials` показывают принятые и
нерешённые задачи. Расход обеих групп сохраняется отдельно; средний расход
на принятую задачу включает затраты всей серии. Подробнее —
[цикл выполнения и учёт расхода](native-workflow.md).
