# Исполнитель, проверки и ревью

`workflow` доводит одно ограниченное задание до пройденных проверок и отдельного
ревью. Codex в основном чате задаёт требования, выбирает проверки и принимает
итог. Команда не меняет модель основного чата и не заменяет проверку интеграции.

## Запуск

Нужны настроенный Orchestra-проект, Python 3.11+, авторизованный Codex CLI
и macOS, Linux или WSL. Подготовьте обычный worker-job для `execute` с шестью
разделами brief, командами проверки и `evidence_files`. В `evidence_files`
перечислите код, тесты и другие файлы, от которых зависит правильность решения.
Формат задания приведён в [справочнике выполнения](../skills/orchestra/references/execution.md).

```bash
# Проверить задание и маршрут без запросов к модели.
./bin/orchestra workflow /path/to/project --input job.json --max-launches 6 --dry-run

# Запустить исполнителя, проверки, ревью и разрешённые исправления.
./bin/orchestra workflow /path/to/project --input job.json --max-launches 6
```

Рабочий цикл:

1. Исполнитель выполняет исходное задание. Хост запускает назначенные проверки.
2. Если проверки прошли, отдельный проверяющий читает требования и итоговые файлы.
3. При `VERDICT: FAIL` исполнитель получает исходные критерии и замечания.
   При ошибке теста он получает краткую диагностику со ссылкой на полный журнал.
4. После исправления проверки и независимое ревью запускаются снова.

Лимит `workflow.max_repair_cycles` общий для исправлений после тестов и ревью.
При двух разрешённых исправлениях потребуется не более шести запусков:
три исполнителя и три проверяющих. Если задан меньший `--max-launches` или
`workflow.max_launches`, цикл остановится раньше. Каждый лист запускается
в новом процессе. Для других уровней проверки, например финального ревью
всей интеграции в strict/program, остаются обычные обязанности основного чата.

## Когда нужен более сильный профиль

Причину ошибки задаёт хост в `checks[].failure_cause`, а не текст ответа модели.

| Причина | Действие |
| --- | --- |
| `implementation` | Первое исправление на прежнем профиле; повторное может перейти на следующий настроенный профиль. |
| `context` | Вернуть задачу основному чату, чтобы найти недостающие сведения. |
| `environment` | Остановиться и разобраться с окружением. |
| `capability` | Вернуть задачу основному чату для проверки доступных инструментов. |

Конкретный отказ ревьюера считается ошибкой реализации. Сбой процесса,
непонятный ответ, повреждённое доказательство или прерывание не дают разрешения
на автоматическую эскалацию. Две одинаковые неудачи с неизменными файлами,
диагностикой и теми же настройками модели останавливают ещё один такой же вызов.
Настоящая смена модели, effort или провайдера сохраняет разрешённую попытку.

## Повторное использование проверок

По умолчанию каждый запуск выполняется заново. Для повторяющихся заданий
с известными входами можно явно добавить:

```bash
./bin/orchestra workflow /path/to/project --input job.json --max-launches 6 \
  --reuse --environment conditions.json --dependencies dependencies.json
```

`conditions.json` — объект с существенными условиями, например
`{"database":"fixture-v1","dependencies":"locked"}`. `dependencies.json` —
список относительных путей к lock-файлам, проверкам, входным данным и другим
зависимостям. Если дополнительных файлов нет, укажите `[]`. Не помещайте сюда
ключи, пароли или токены доступа.

Повторное использование возможно при совпадении задания, критериев, команд,
настроек, объявленного окружения и содержимого файлов. Конфигурация Orchestra,
политики проекта и доступный `AGENTS.md` также входят в проверку. Сохранённые
журналы и заключение перепроверяются: изменённый файл или доказательство
аннулирует совпадение. Кэш хранится локально в `.orchestra/verification-cache`.

При `fresh_reviewer_always = true` проверяющий всегда запускается заново;
совпадение позволяет пропустить повторную работу исполнителя. Повторное
использование самого ревью требует явного `--reuse` и
`fresh_reviewer_always = false`. Эти настройки не меняются автоматически.

Перечень зависимостей задаёт человек или основной чат. Команда не может узнать
о неуказанном внешнем сервисе, скрытом входном файле или изменившейся базе.
Для таких задач оставьте повторное использование выключенным.

## Расход и незавершённые задачи

Итог сохраняется в `.orchestra/workflows/UUID.json`. Он содержит все вызовы
исполнителя, исправления, ревью, причину остановки и ссылки на доказательства.
Входные токены уже включают кешированные; повторно они не прибавляются.
Пропущенные счётчики остаются неизвестными и останавливают новые вызовы.
Порог `max_observed_tokens` проверяется перед каждым следующим вызовом и
не ограничивает уже запущенный запрос или денежную стоимость.

При использовании прежнего доказательства в текущем запуске нет нового
модельного расхода; ссылка ведёт к исходной проверке. Её прежние затраты
остаются в исходном запуске. Нулевой новый расход не означает бесплатное
получение исходного решения. Работа основного чата и разработка Orchestra
в эти счётчики не входят.

Учебный `eval run` использует тот же цикл. Отчёт отдельно показывает принятые
и нерешённые задачи и расход обеих групп. `observed_tokens_per_accepted_trial`
делит общий расход серии, включая неудачи, на число принятых задач.
Этот показатель нужно читать вместе с числом нерешённых задач. Сам по себе
он не доказывает экономию или сохранение качества.

При аварийном прерывании остаются `workflow.lock` и запись текущего этапа.
Сначала проверьте процессы и журналы. Удаление блокировки не доказывает,
что запрос не выполнился; автоматического продолжения с повтором вызова нет.
