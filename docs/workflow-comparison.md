# Сравнение рабочего процесса и диагностика

`compare-workflows` сравнивает варианты процесса на одних заданиях и моделях.
Он не запускает модели, не меняет настройки и не оценивает стоимость в деньгах.

```bash
./bin/orchestra compare-workflows "<проект>" --input samples.json \
  --profile cheap --variant before --variant after --baseline before
```

`samples.json` содержит массив объектов с двумя полями: `variant` и `sample`.
Внутри `sample` используется формат `calibrate`: `fixture_fingerprint`,
`receipt`, `quality` и `elapsed_seconds`. Receipt содержит все попытки, включая
неудачи, отмены и эскалации; у каждой попытки есть профиль, запрошенная модель,
effort и наблюдаемый usage. Отсутствующие счётчики остаются неизвестными.

Для каждого варианта нужны одинаковые задания и число повторений по каждому
профилю. Начальная запрошенная модель и effort должны совпадать. В fingerprint
включайте хэши исходников, исходный запрос, критерии, окружение и версию
использованной обвязки. Сами секреты или полные личные данные туда не добавляйте.

Отчёт проверяет качество отдельно по каждому заданию и профилю: одинаковая
общая доля успехов не скрывает провал на другом задании. Рекомендация появляется,
если все результаты кандидата прошли, нет ухудшения по заданиям, данные полны
и наблюдаемый общий расход ниже. Это вывод по переданному набору, не гарантия
для будущих задач. Значения качества передаёт проверяющий: команда сама не
перезапускает проверки и не подтверждает достоверность receipts.

`observed_total_tokens_percent_change` выражен в процентах: `-7.35` означает
снижение примерно на 7,35%. Кэшированный вход уже входит в `input_tokens`.
Не прибавляйте его повторно и не считайте все токены одинаковыми по цене.
Фазы работы остаются неизвестными без подходящих событий выполнения.

## Диагностический контекст для повторной попытки

В существующей таблице `[context]` файла `.orchestra/project.toml` установите:

```toml
[context]
repair_context = "diagnostic"
```

Затем выполните `sync` и `doctor`. Режим ищет строки с диагностикой в сохранённом
логе и добавляет краткий конец вывода, реальную команду проверки, код возврата
и ссылку на очищенный артефакт. Нового запроса к модели для этого нет.
Исходная задача и критерии сохраняются. Режим применяется к повторным попыткам
нативного `execute`; он не меняет процесс произвольного главного чата.

Значение `tail` сохраняет прежний контекст из конца последнего лога и остаётся
значением по умолчанию. Переключайтесь после сравнения на своих задачах.
Если обязательные сведения не помещаются в бюджет brief или лог небезопасен,
повторный запуск останавливается и возвращает проблему главному агенту.

## Чтение нужного участка лога

```bash
./bin/orchestra log search "<проект>" \
  .orchestra/checks/<запуск>/attempt-1-check-1.log --query ValueError

./bin/orchestra log read "<проект>" \
  .orchestra/checks/<запуск>/attempt-1-check-1.log --start-line 20 --max-lines 30
```

По умолчанию вывод краткий: путь, номера строк и текст. В конце указаны
`more`, `next_start_line` и `incomplete`. Используйте следующий номер строки для
продолжения; `incomplete=true` означает, что весь вывод считать прочитанным
нельзя. `--json` возвращает структурированный результат.

Поиск буквальный, без регулярных выражений. Читаются только сохранённые файлы
в `.orchestra/checks` и `.orchestra/executions`. Проверяются путь, тип файла,
размер и ссылки; известные секреты скрываются. Ограничения хранения логов
сохраняются, включая отметку об усечённом выводе. Файлы не изменяются.
