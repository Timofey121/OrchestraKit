# Первое подключение проекта

Это руководство рассчитано на первый запуск OrchestraKit с локальным проектом
и Codex. Основной путь использует полную папку набора: исходный каталог или распакованный
архив. В командах замените каждый фрагмент в угловых скобках на свой путь или
своё название. Скобки в команду не копируйте.

Например, вместо `<путь-к-проекту>` укажите путь к каталогу, который хотите
подключить. Не используйте путь к самой папке OrchestraKit вместо пути проекта.

## 1. Проверьте окружение

Нужен Python 3.11 или новее. Во время работы OrchestraKit использует стандартную
библиотеку Python. Для чатов подойдёт Codex Desktop или CLI. CLI в `PATH`
понадобится для нативной команды `execute`. Node.js не нужен для запуска панели, но потребуется, если вы
будете менять её исходники и собирать фронтенд.

```bash
python3 --version
codex --version
```

Первая команда должна показать Python 3.11 или новее, например `3.11.5` или
`3.12.0`. Вторую проверяйте, если планируете нативный запуск. Версия Codex и набор
доступных в нём моделей зависят от вашей установки, поэтому не копируйте чужие
идентификаторы моделей без проверки.

Нативное выполнение исполнителей поддерживается на POSIX-хостах, включая macOS
и Linux. На Windows используйте WSL для нативного выполнения. Панель читает
локальные данные через Python, но это не добавляет нативный запуск в Windows.

Для полного сценария на Windows запускайте Codex CLI и OrchestraKit внутри
одного окружения WSL: установка, подключение проекта и панель должны видеть
одни и те же файлы Codex. В WSL используйте команды ниже, как на Linux.
Отдельная проверка Windows в CI охватывает установку Python-набора и панель,
но не подтверждает запуск хуков в Windows-хосте Codex или нативных исполнителей.
macOS и Linux проходят полный набор тестов на Python 3.11 и 3.13.

## 2. Подготовьте папки

Получите полную папку OrchestraKit и выберите существующий каталог проекта.
Для нового проекта сначала создайте папку. Команда `init` подключает её к
Orchestra, но не создаёт исходники вашего приложения. У проекта могут
уже быть исходники и Git-репозиторий, но это не обязательно для первоначальной
настройки.

```bash
cd "<путь-к-OrchestraKit>"
ls
```

В выводе должны быть `bin`, `src`, `skills`, `templates` и файл `README.md`.
Если этих файлов нет, вы находитесь не в корне набора или получили неполный
архив.

## 3. Установите OrchestraKit

Из корня OrchestraKit выполните:

```bash
./bin/orchestra setup
```

Команда устанавливает навык в `~/.agents/skills/orchestra`, добавляет управляемое
правило в глобальные инструкции Codex и готовит определения hooks. В навык
входят Python-код, шаблоны и собранные файлы панели. В конце команда проверяет
установленные файлы и завершается с кодом `0`, если они совпадают с полученным
набором.

Если Codex хранит домашние данные не в стандартном месте, укажите каталог явно:

```bash
./bin/orchestra setup \
  --codex-home "<путь-к-Codex-home>"
```

Для проверки без изменений выполните:

```bash
./bin/orchestra setup --check
```

Затем откройте `/hooks` в Codex, прочитайте определения и подтвердите доверие
через интерфейс хоста. Команды `setup` и `setup --check` проверяют только файлы.
Они не могут подтвердить доверие вместо пользователя и выводят
`runtime_trust: unknown`.

После установки можно запускать OrchestraKit из другой папки. Этот запускатель
содержит нужные файлы и не требует, чтобы исходная папка набора оставалась на
прежнем месте:

```bash
python3 ~/.agents/skills/orchestra/scripts/orchestra.py --help
```

## 4. Подключите проект

Вернитесь в папку OrchestraKit или используйте установленный запускатель.
Создайте проектную интеграцию:

```bash
cd "<путь-к-OrchestraKit>"
./bin/orchestra init "<путь-к-проекту>" --name "Название проекта"
```

Ожидаемый результат: в `<путь-к-проекту>` появится каталог `.orchestra` с
`project.toml`, а также управляемые файлы инструкций и ролей. `init` сохраняет
ваш существующий текст в `AGENTS.md` и отказывается заменять пользовательские
файлы там, где ожидает свой управляемый файл.

Проверьте подключение:

```bash
./bin/orchestra doctor "<путь-к-проекту>"
```

При успехе команда сообщает, что конфигурация и сгенерированные файлы в порядке,
и завершается с кодом `0`. Если она показывает ошибку, сначала устраните её.
При сообщении о дрейфе выполните `sync`, затем повторите проверку:

```bash
./bin/orchestra sync "<путь-к-проекту>"
./bin/orchestra doctor "<путь-к-проекту>"
```

Перед первой задачей проверьте названия моделей в `.orchestra/project.toml`.
Шаблон содержит примеры, доступность которых зависит от вашей установки Codex.
Если поменяли профиль, выполните `sync` и `doctor`, как описано ниже.

## 5. Откройте новый чат Codex

Откройте `<путь-к-проекту>` как основную папку нового чата Codex. Новый чат
важен после создания или синхронизации интеграции: он получает актуальные
инструкции проекта и описания ролей.

Опишите задачу через результат и проверку. Например:

```text
Добавь фильтр по статусу в список заказов. Сохрани существующее поведение,
добавь проверку нового фильтра и покажи, какая команда прошла.
```

Небольшая связанная задача выполняется главным агентом прямо в чате. Если проект
ещё не подключён, для такой задачи не нужны `init`, файлы конфигурации или
исполнители. Когда задача имеет независимые части, можно написать:

```text
Use $orchestrate-project for this task. Проверь итог перед тем, как завершать работу.
```

Главный агент остаётся ответственным за выбор работы, итоговую проверку и
объединение изменений. Исполнитель получает отдельное ограниченное задание.

## 6. Настройте профили исполнителей

Откройте файл:

```text
<путь-к-проекту>/.orchestra/project.toml
```

Профиль связывает имя модели и значение effort. Роли ссылаются на профили.
Главный чат использует модель, выбранную в Codex, поэтому изменение профиля не
меняет активную модель главного чата.

В шаблоне есть примеры `gpt-5.6-luna`, `gpt-5.6-terra`, `gpt-5.6-sol` и
`gpt-6-astra`. Это имена из шаблона, не общий список доступных моделей. Их
доступность и допустимые уровни effort проверяются в вашей среде.

После изменения `project.toml` всегда выполните команды ниже до делегирования
или открытия следующего чата:

```bash
./bin/orchestra sync "<путь-к-проекту>"
./bin/orchestra doctor "<путь-к-проекту>"
```

`sync` обновляет только файлы с маркером OrchestraKit. Файл `project.toml` остаётся
проектным источником настроек.

## 7. Откройте локальную панель

Панель показывает доступные локальные записи задач, попыток, чатов и счётчиков.
После `setup` запустите её из любой папки:

```bash
python3 ~/.agents/skills/orchestra/scripts/orchestra.py ui
```

Ожидаемый результат: команда выводит адрес наподобие
`http://127.0.0.1:8731` и держит сервер в текущем терминале. Откройте этот
адрес в браузере. Сервер доступен только на loopback-интерфейсе. Пока терминал
работает, панель обновляет наблюдения; `Ctrl+C` останавливает сервер.

Для другого порта и ручного открытия браузера:

```bash
./bin/orchestra ui "<путь-к-проекту>" --port 8732 --no-browser
```

В панели можно выбрать «Все проекты». Если нужного каталога нет в локальных
записях Codex, передайте его путь после `ui`. Чтобы смотреть только явно
указанные Orchestra-проекты, добавьте `--no-codex`:

```bash
python3 ~/.agents/skills/orchestra/scripts/orchestra.py ui \
  "<путь-к-проекту>" --no-codex
```

Статус `unknown`, пустое поле или прочерк говорят об отсутствии доступного
наблюдения. Панель не превращает эти значения в оценку денег, не учитывает
непрочитанные облачные данные и не подтверждает, что сохранённая запись означает
действительно работающий процесс.

## 8. Добавьте внешний провайдер при необходимости

Внешний провайдер задаётся в
`<путь-к-проекту>/.orchestra/project.toml`. Нужны его адрес API, имя переменной
с ключом, модели и заявленные возможности инструментов. Секрет хранится вне
TOML: в переменной окружения процесса Codex или, в macOS, в Keychain.

```bash
export EXAMPLE_API_KEY="<ваш-ключ>"
```

Не добавляйте значение ключа в проект, примеры команд, документацию или коммит.
Переменная окружения имеет приоритет перед Keychain. Поддерживается только
Responses-совместимый API. Перед назначением профиля проверьте документацию
провайдера: набор инструментов может отличаться от возможностей Codex.

После настройки выполните:

```bash
./bin/orchestra sync "<путь-к-проекту>"
./bin/orchestra doctor "<путь-к-проекту>"
```

`doctor` проверяет локальную конфигурацию, наличие нужного ключа и путь к
каталогу моделей. Он не выполняет тестовый запрос к внешнему API.
Конкретный пример есть в [настройке DeepSeek](providers/deepseek.md).

## 9. Проверьте hooks

`setup` уже подготовил hooks. Повторно проверьте их файлы командой:

```bash
./bin/orchestra setup --check
```

Затем в Codex откройте `/hooks`, прочитайте каждое добавленное определение и
подтвердите доверие согласно интерфейсу хоста. Установка и проверка файлов сами
по себе не означают, что хост будет запускать hooks. Они также не дают гарантии
экономии токенов. Ограничения описаны в [документе о hooks](hooks-and-orchestration.md).

## 10. Обновите набор и проект

Для обновления получите новую полную папку OrchestraKit. Перейдите в неё и
повторите:

```bash
cd "<путь-к-новому-OrchestraKit>"
./bin/orchestra setup
./bin/orchestra sync "<путь-к-проекту>"
./bin/orchestra doctor "<путь-к-проекту>"
```

Откройте новый чат проекта после синхронизации. Если вы используете hooks,
проверьте их определения в `/hooks` ещё раз.

## Следующие шаги

Для ежедневной работы обычно хватает `doctor`, нового чата и понятных критериев
готовности в задаче. Команда `usage` сводит доступные счётчики из переданных
журналов, но значения `unknown` остаются неизвестными и не являются данными о
счёте.

Полный формат профилей, ролей и режимов работы описан в
[конфигурации проекта](project-config.md). О панели подробнее рассказывает
[руководство панели](local-dashboard.md). Состояние задач, очередь, ревью и
изоляция работы относятся к расширенному сценарию; их справочник находится в
`~/.agents/skills/orchestra/SKILL.md` после установки навыка.

Если вы меняете сам OrchestraKit, выполните его тесты из корневой папки:

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

## Установка как Python-пакета

Этот вариант даёт команду `orchestra` в отдельном Python-окружении. Публикация
пакета в PyPI не требуется: устанавливается полученная папка исходников.
Сборка может скачать зависимости setuptools из реестра пакетов; у самого
OrchestraKit нет сторонних зависимостей времени выполнения.

```bash
cd "<путь-к-OrchestraKit>"
python3 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/orchestra --help
.venv/bin/orchestra setup
```

После установки пользовательский навык запускается обычным Python, как в
основной инструкции. Для обновления пакета повторите `pip install` из свежей
папки набора, затем обновите навык и синхронизируйте проекты. Устанавливайте
пакет в своё окружение, без `sudo` и изменения системного Python.
